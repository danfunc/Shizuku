# 03. 方針: 設計文書 → 現行リポジトリ流儀への写像

ここは「PORT §5 の層構造」と「現行リポジトリの組み方」を突き合わせて、
新実装のディレクトリ・型・名前を確定させる文書。**決定 (D-n)** と **未決 (Q-n)** を分けて書く。
未決はユーザーに確認するか、着手時に「暫定」と明記して進める。

## 1. 層構造の写像

PORT §5 の提案:

```
arch/<isa>/   文脈退避・例外フレーム・特権遷移・atomic・タイマ割り込み (ISA ごとに書く唯一の層)
board/<board>/ コア起動・時刻・UART/USB・DMA・ペリフェラル・クロック API
kernel/       スレッド・文脈・呼び出しフレーム・実行権委譲 (オブジェクト概念なし)
kobj/         カーネルオブジェクト: オブジェクト表・メソッド解決・svcルート・md (全ISA共通)
objects/      ドライバ / アプリ
```

これを現行リポジトリの流儀 (internal_headers + templates + concepts + modules + configs) に写像する:

| PORT の層 | 置き場所 | 形 |
|---|---|---|
| **kernel** (機構・ISA 非依存) | `internal_headers/shizuku/templates/kernel.hpp` ほか + `source/` | `templates::kernel<ARCH, BOARD, …>` クラステンプレート。実装は config.hpp で確定した別名への `template<>` 特殊化 (.cpp) |
| **arch** | `modules/<port>/internal_headers/shizuku/archs/<isa>.hpp` + `<isa>_ctx.S` | kernel のテンプレートパラメータ。`concepts::arch_requires` で縛る。現行の `cpu_drivers/` を **`archs/` に改名・再定義** (D2) |
| **board** | `modules/<port>/internal_headers/shizuku/boards/<board>.hpp` + .cpp | 同上 (`concepts::board_requires`)。現行の `memory_managers/` の役割を包含し、時刻・コア起動・クロック API も持つ |
| **kobj** | `internal_headers/shizuku/templates/kernel_object.hpp` + `source/kernel_object/` | ISA 非依存の C++。kernel テンプレートとは**別クラス**。カーネルからはハンドラとして起こされ、プリミティブ (CALL/RETURN) を撃ち返す |
| **objects** | **別リポジトリ「XNO」** (D17) | Shizuku 本体に残るのはカーネル検証用の自己テストオブジェクトのみ |
| 型注入・構成 | `configs/config_template.hpp.in` (現行機構を維持) | `SHIZUKU_ARCH` / `SHIZUKU_BOARD` / `SHIZUKU_CPU_COUNT` 等の kit 変数で確定 |

## 2. 決定事項 (設計文書由来。再議論しない)

- **D1. カーネルはオブジェクトを知らない** (PORT §3 / DESIGN §7)。カーネルが知るのは
  スレッド / 文脈 / スタック上限 / 呼び出しフレーム / 登録ハンドラ entry /
  スケジューリング機構 / MPU region だけ。`templates::kernel` から `OBJECT_T`
  パラメータと `object_table` を**外す** (現行骨格からの最大の変更点)。
  **identity (cookie) すらカーネルには無い** — 「誰がどのオブジェクトとして走って
  いるか」は kobj が自分の台帳 (影スタック) で追う。カーネルが持つのは
  「この枠はハンドラを起こしたものか」の 1 ビットだけ (§3.6.1)。
- **D2. arch と board を分離**し、cpu_driver という名前は廃止 (01 §4-6 のねじれ解消)。
  最初の実体は `archs::armv8m` (RP2350) と `boards::rp2350_pico2` (pico-sdk ベース)。
  ※ 参照実装の実績があるのは RP2350。RP2040 (ARMv6-M) は PORT §6 の移植順序 3 番目以降。
- **D3. カーネルプリミティブは 4 種** (DESIGN §7.2 から REDISPATCH と SET_HANDLER を
  削除。経緯と根拠は §3.6 / 2026-08-19 改定):
  `CALL(call_request*)` / `RETURN(n, value, err, depth_claim)` /
  `SWITCH(tid)` / `GRANT(tid, us)`。
  - I-1: svc 番号で経路を分岐しない。**経路は呼び出しフレームの段数のパリティ
    だけで決まる** — 偶数段 = オブジェクト、奇数段 = ハンドラ。フレームを積むのは
    トランポリンと CALL の 2 つだけで必ず交互になるので、段数がそのまま実行主体を
    表す。旗も cookie も要らず、段数を書けるのはカーネルだけなので偽装もできない
  - I-2: プリミティブを撃てるのはカーネルオブジェクトのハンドラだけ。上の判定
    そのものが保証するので、検査して弾くコードは存在しない
  - **カーネルは identity (cookie) も信頼ビットも持たない**。誰が誰かは kobj の台帳
    (PORT §3.1「呼び出し元 identity はカーネル支援不要」)
  - ハンドラの登録は syscall ではなく系の組み立て (`set_object_handler`)
  - `protection` = 実行特権 + (将来) region set (DESIGN §11.3)
- **D4. 委譲は kobj のメソッド呼び出しで行う** (PORT §4.6 改め)。カーネルが持つのは
  「オブジェクトランドの svc ハンドラ」の入口 1 個だけで、番号 → 担当の表は kobj 側。
  identity は kobj の台帳から取るので、呼び出しに identity 引数は要らない。
- **D5. exit はオブジェクトランドの exit API 経由**。オブジェクトは RETURN を撃て
  ないので、(a) カーネルがハンドラを起こすとき**今のネスト数を渡し**、
  (b) オブジェクトは exit API に**何段戻すか**を載せて撃ち、
  (c) ハンドラが `RETURN(n, value, err, depth_claim)` で巻き戻す (1 段 = 2 枚)。
  段数は必ず申告し、カーネルが実際の深さと突き合わせる (§9.3)。
  **戻り口はカーネルの 1 本だけで、呼び出しごとに指定しない** — その戻り口が撃つ
  RETURN は、ハンドラから出ればプリミティブ、オブジェクトから出れば経路判定で
  exit API としてハンドラへ届く (だから exit API の番号は RETURN と同値)。
  REPLACE モードは作らない。
- **D18. ペリフェラルオブジェクトは board モジュールが持ち、特権を宣言する**
  (2026-08-20 ユーザー提案)。`spi_init` のような操作は RESETS/CLOCKS を触るので
  本質的に特権側かつ SoC 固有。**ペリフェラルオブジェクトが特権を引き受けることで、
  その上のドライバ (XNO 側) を非特権のままにできる** — DESIGN §11.2 の
  「ドライバは非特権で走れる。IO を触るから特権ではない」を成立させる分担。
  生成時に `OBJECT_PRIVILEGED` を宣言し、kobj の `object_protection()` が
  Phase 5 (MPU) でそれを実際に効かせる。現状は全オブジェクト特権 (MPU が無いので
  非特権にしても隔離にならず pico-sdk が黙って壊れるだけ = §11.2.1)。
- **D6. 特権の静的クラスを作らない** (DESIGN §11.6 / PORT §4)。信頼ビットは 1 個。
  サブカーネルへの特権貸し出しはしない (overhead を払う。決着済み 2026-08-17)。
  現行骨格の `obj_type::PRIVILEGED_LAND_OBJECT` 系 enum は削除し、オブジェクト属性は
  kobj 側の表 (軸 C) + CALL の protection 引数 (軸 A/B) で表す。
- **D7. md はカーネルオブジェクトが持つ** (DESIGN §12.3)。ただし実装は
  §17 の順序 (identity → 親子 → md → arena) を厳守。順序を飛ばした md 単体実装は無意味。
- **D8. 表は最初から疎に** (PORT §5.3)。`static_table<T,128>` の直接使用ではなく、
  スロット確保 (CAS 予約) 付きの疎テーブルテンプレートを `templates/table.hpp` に追加する。
  会計 (使用量に比例した予算) の前提。
- **D9. アトミック操作は arch パラメータ** (DESIGN §14.5.3)。CAS / release store /
  acquire load を concept 要件にする。ktab_lock (コア間共有表の短スピンロック) も
  arch の CAS 上に作る。svc ハンドラ内では block/yield 禁止 (純スピン)。
- **D10. 例外優先度規約 (svc 最優先 > タイマ > 切替最低) は arch の要件として明記**
  (DESIGN §14.5.1)。concept のコメント + arch ごとの自己テストで守る。
- **D11. クロック変更は board 層 API** (PORT §2.3 / XIP_FLASH_CLOCK.md)。
  上位 (kernel/kobj/objects) はクロックを直接触らない。
- **D12. エラー方針 = I-9**。一般オブジェクト起因の失敗はすべてエラー復帰。
  panic はカーネル自身の不変条件破れのみ。**共通するのは「黙って捨てない」**で、
  返す先があるならエラー、無いなら panic (未知の svc 番号は、オブジェクトランドの
  ハンドラなら発行元へエラー返却、カーネルのプリミティブ選択なら panic — §3.6.1)。
  C++ 内 API は `templates::result<T>`、svc ワイヤは 0=成功の型付き enum
  (参照実装 `error_t<E>` の形を templates/result.hpp の隣に移植)。
- **D13. 言語は C++ (template + concepts)** (PORT §5.6)。現行リポジトリの流儀とも一致。
- **D14. 自己テストは最初から** (DESIGN §16)。梯子式 (1 段 → N 段)、identity e2e、
  状態の自己申告 (MRS CONTROL 等)、カウンタは期待値と突き合わせ、拒否のテスト。
  検証インフラ (固まっても出る診断経路 / panic ring / svc trace) も最初から (PORT §7)。

- **D15. ビルドシステムは Bazel** (2026-08-19 ユーザー確認済み:「Bazel でもいいし
  おそらくそっちの方が望ましい」)。再検討の結果と根拠は §3.5 参照。
  移行戦略: **CMake は Bazel bring-up が完了するまで並存させ、同等性確認後に削除**。
  configs/config_template.hpp.in の型注入機構は Bazel でも維持できる
  (`expand_template` / genrule で同じ config.hpp を生成する)。
- **D16. カーネルコアの言語は C++ を維持、Rust はオブジェクト層の将来オプション**
  (再検討の結果。§3.5 参照)。svc + メソッド呼び出しの安定 ABI 境界を保つことが
  「後から Rust オブジェクトを足せる」ための前提条件なので、ABI 境界の設計時に
  C++ 固有機能 (例外・RTTI・C++ 型のワイヤ露出) を跨がせないこと。
- **D17. オブジェクト集合 (ドライバ / アプリ) は別リポジトリ「XNO」に分離**
  (2026-08-19 ユーザー指示。XNO = 苦悩, "X Not an Object")。
  - Shizuku リポジトリに残るもの: kernel / **kernel object (kobj)** / arch / board /
    configs / **カーネル自己テスト用オブジェクト** (DESIGN §16 のテスト群はカーネルと
    同居しないと検証が回らない)。ユーザー確認済み:「kernel object は含めていいが、
    Shizuku を XNO ほど大規模にする理由はない」— Shizuku 本体は**小さく保つのが目標**
    (カーネル + 信頼境界内の最小構成のみ)
  - XNO 側に置くもの: 実ドライバ (BLE/BME280/BNO055/WS2812/USB 等の移植)、
    アプリ (TELEMETRY 等)、System Object / セッション / ユーザー等の上位構成
    (DESIGN §4.4 の階層) も方針オブジェクトなので XNO 側が自然
  - 境界 = **svc + メソッド呼び出しの安定 ABI** (D16 と同じ境界)。Shizuku は
    ABI ヘッダ (svc ラッパ・obj_api 相当・stream ライブラリ) を「公開ヘッダ」として
    エクスポートする必要がある — internal_headers と別に `public_headers/` 系の
    区分を設けること (現行は internal しか無い)
  - Bazel 化 (D15) と噛み合う: XNO は `bazel_dep` + `git_override` で Shizuku を
    引く。参照実装が 1 ディレクトリにカーネルとアプリを混ぜて負債化した反省とも整合
  - 未決: XNO リポジトリの作成タイミングと、stream.hpp のような「ライブラリだが
    データプレーン」の所属 (暫定: Shizuku 側の公開ヘッダ)

- **D18. スレッドの記憶はカーネルの資源ではない** (2026-08-20 ユーザー提起:
  「これスレッドってカーネルの資源になっちゃってるよね。それは渋いな。スレッド
  テーブルのメモリはオブジェクトランドから与えられるようになっていた方が好ましい」)。
  - カーネルは固定長のスレッド配列を持たない。`set_thread_storage(memory, bytes)` で
    **貸してもらった記憶**をスレッド表として据え、**何本作れるかは渡された量が決める**。
    スタックも同じで、`spawn_request` に `stack_base` / `stack_bytes` を載せて
    呼ぶ側 (kobj) が用意する。**スレッド 0 も例外にしない** —
    `bootstrap(entry, stack_base, stack_bytes)` として貸し出しに揃えた
    (ここだけカーネルが malloc すると「スレッドの記憶は誰のものか」が二枚舌になる)
  - DESIGN §4.1 ルール 1「オブジェクトが資源を持つ」の直接の帰結。カーネルが
    THREAD_COUNT を持っていた時点で、カーネルは「何本まで許すか」という**方針**を
    持ってしまっていた (D1 違反)
- **D19. 所有 (誰が出すか) と保護 (どこに置くか) は別問題** (2026-08-20 ユーザー懸念:
  「まぁでもそうするとMPU保護region的に渋いかな...」への回答)。
  - 懸念は正しい。カーネルの簿記が非特権から届く場所にあると、非特権オブジェクトが
    他スレッドの文脈を書き換えられる = MPU を張った意味が消える
  - しかしそれは**出どころの問題ではなく置き場所の問題**。そこで kobj は arena を
    2 つ持つ:
    - **簿記用 arena** = 静的領域 (.bss)。region の外 = PRIVDEFENA により特権のみ。
      スレッド表はここから貸す
    - **オブジェクト用 arena** = ヒープ (region1)。非特権から届く。スタックや
      オブジェクトの作業領域はここから貸す
  - 置き場所の条件は「気をつける」では守れないので、**カーネルが検査する**:
    `set_thread_storage` は `base >= BOARD::unprivileged_floor()` なら panic する。
    貸すのはオブジェクトランド、条件を課すのはカーネル、という分担
- **D20. オブジェクトランドのメモリ授受 API** (2026-08-20 ユーザー指示:
  「オブジェクトランドにメモリの受け渡しができる機能があった方がいい
  (object memory は簡易な一つの形だけど、これにとらわれる必要はない)」)。
  - 参照実装の「オブジェクトごとに固定 16 語」は簡易な一形態にすぎないので踏襲しない。
    `MEMORY_ALLOCATE` / `MEMORY_RELEASE` / `MEMORY_HAND_OVER` / `MEMORY_OWNER` を置く
  - **持ち主を記録する**のが要点。持ち主が判るので (a) 他人のものは返せない
    (`NOT_OWNER`)、(b) `HAND_OVER` で持ち主を**付け替える** = 渡した側は以後返せない、
    という 2 つが同時に成立する。「渡したのにまだ自分のもの」という曖昧さが残らない
  - 持ち主は発行元から導出する (名乗らせない)。EXPORT_METHOD と同じ作法
- **D21. flash FS は XIP 前提で「アドレスを返す」** (2026-08-20 ユーザー提起:
  「flash FS オブジェクトがあってもいいかもね。fat 系だと XIP 前提ではないし、
  XIP 前提でアドレス保存なやつがあっても良いでしょう」「flash FS object は
  pico-sdk support モジュールの一環として実装されるべき」)。
  - FAT 系は「媒体はブロックの列で、読むとは buffer へ写すことだ」という前提で
    組まれている。RP2350 では flash が XIP で 0x10000000 にそのまま見えているので、
    その前提はこの機械では嘘になる。`lookup("foo") → アドレス + 長さ` を返し、
    **写さない**。中身がコードならその場で実行できる
  - 代償を隠さない: **配ったアドレスは動かせない**ので、削除は名前を空けるだけで
    領域は詰め直さない (詰めるとアドレスがずれ、配った参照が腐る)。回収は FORMAT
  - 置き場所が pico_sdk_support である理由: 消去・書き込みの間は **XIP ごと止まる** =
    flash 上のコードを誰も実行できない。ミリ秒単位で系全体が止まるので、これは
    「たまたま特権命令を使う」のではなく**系を止める権利**を持つ操作。読むほうは
    ただのメモリ読み出しなので、引いた後は非特権オブジェクトでも自分で読める

- **D22. カーネルはライブラリとして提供する** (2026-08-20 ユーザー提起:
  「ふと思ったけどカーネルは本来ライブラリとして提供されるべきじゃないか」)。
  - **そうすべきで、しかも D18 の時点で実質そうなっていた**。資源を持たず
    (スレッド表もスタックも貸してもらう)、方針を持たず、`main` も持たない層は、
    定義からしてライブラリ以外になりようがない。実行ファイルだったのは
    ビルド設定の惰性であって設計ではなかった
  - 目標構成:
    - `shizuku_kernel` … 機構 (kernel + cpu_manager)
    - `shizuku_kernel_object` … 方針。**カーネルとは別ライブラリ**
    - `shizuku_selftest` … カーネルを使うオブジェクトの集合
    - `firmware/` … **合成だけ**を持つ唯一の実行ファイル (main.cpp)
    - `modules/pico_sdk_support` … ボード。型 (`:headers`) と実装を分ける
  - ★分けること自体が検算になる: `libshizuku_kernel.a` に `kernel_object` の
    シンボルが 1 つも無いことを `nm` で確かめられる (実測 0 個)。D1
    「カーネルはオブジェクトを知らない」を、主張ではなく**機械が確かめられる形**に
    できたのはこれが初めて。1 つの実行ファイルに混ぜていた間は、うっかり結合しても
    誰も気づけなかった
  - カーネル ↔ ボードの循環は設計上の事実なので隠さず宣言する (例外の入口は
    カーネルへ入り、カーネルは `BOARD::panic` を呼び返す)。ただしカーネルが
    依存するのは**型の継ぎ目**だけなので、`pico_sdk_support_headers` を分けて
    そちらへ依存させる
  - D17 (XNO 分離) の前提条件でもある。XNO は実行ファイルには依存できない —
    3 つのライブラリを引いて**自分の合成を書く**のが XNO 側の仕事になる
- **D23. オーバークロックは今は入れない。ただし理由は「SPI が上げられないから」ではない**
  (2026-08-20 ユーザー示唆:「速度が足りなさそうなら、リファレンス実装にオーバー
  クロックの方法が載ってる」→「SPI 周波数を上げることは可能。CYW43 の定格による」)。
  - ★**最初に書いた理由付けは誤りだった**。「参照実装は SPI を 75MHz に据え置く設計
    だから clk_sys を上げても LED は速くならない」と書いたが、あの 75000 は
    `SHIZU_CYW43_SPI_TARGET_KHZ` という**変えるために置かれた cache 変数**で、
    上限ではなく「既知良」。しかも 75MHz は SM クロックで、PIO が 1 ビット 2 命令
    使うので**実 SCK は 37.5MHz**。上げ代はある (CYW43439 の gSPI 定格 50MHz まで)
  - **実測で決着した (2026-08-20)**: SCK を半分 (37.5 → 18.75MHz) にして
    LED 書き込みの最小値を測った。線速律速なら半分にすれば倍 (+1200µs) になるはず:

    | SCK | n | min | 中央値 | σ |
    |---|---|---|---|---|
    | 37.50 MHz | 21 | 904 | **1196** µs | 721 |
    | 18.75 MHz | 21 | 1152 | **1248** µs | 729 |

    差は **+52µs**。分布は完全に重なっている。**転送そのものは全体の 4% しかない**。
    残りは `cyw43_ll_gpio_set` → `cyw43_write_iovar_u32_u32` の**ioctl 往復**
    (CYW43 のファームウェアが答えるのを待つ) と、寝ていたバスを起こす
    `cyw43_delay_ms(1)`。どちらも SCK に比例しない。
    定格上限の 50MHz まで上げても縮むのは高々 13µs
  - ★測り方を直して初めて分かった: それまで見ていた `led_write` は窓の**最大値**で、
    budget にきれいに追従していた。「SPI が重い」ではなく**呼び出しの途中で
    プリエンプトされた時間が混ざっていた**だけ。最小値 (誰にも邪魔されなかった 1 回)
    を採るようにして初めて操作そのものの費用が見えた
  - ★**分周比は自由なつまみではない**という発見: SDK は PIO プログラムを固定で選んで
    おり (`spi_gap01_sample0` = "for high cpu speed" / `spi_gap0_sample1` =
    "for lower cpu speed")、この 2 つは**応答をサンプルする位置**が違う。位置は SM
    サイクル単位なので、分周比を変えるとサンプル点が実時間でずれる。実測で
    div=2 のまま SCK を 18.75MHz へ落としたら `Failed to read test pattern` で
    チップが上がらなかった — **速くしても遅くしても壊れる**。参照実装の言う
    「固定分周の連鎖」と同じ構図で、今回固定されていたのは分周比ではなく
    **プログラムの選択**のほう。トップの CMakeLists で対にして導出している
  - 揺らぎ (late win) のほうは budget にそのまま追従する (2000µs → 2.1〜2.6ms、
    100µs → 0.2〜0.3ms)。これはスケジューリング方針の数字で、クロックの数字ではない
  - **結論**: 今の 2 つの費用 (ioctl 往復 / スケジューリング方針) はどちらも
    clk_sys に比例しないので、オーバークロックは効かない。効くのは機構の下限
    (〜250µs)、XIP のフラッシュ読み出し (= flash FS の読み)、フラッシュ書き込み中の
    停止時間。参照実装が記録している失敗が「落ちる」ではなく**静かに壊れる**類
    (CYW43 が黙る / フラッシュが読み違える) なので、効く場所が来るまで待つ
  - 引くときの作法 (参照実装 CMakeLists より。**固定分周を直書きしない**が教訓):
    clk_sys 300MHz / vreg 1.20V、CYW43 PIO 分周とプログラムを SCK から対で導出、
    フラッシュ QMI は目標 100MHz から導出、RXDELAY は段数でなく **ps** で宣言
    (5000ps)、clk_peri は PLL_SYS から 150MHz へ分周 (`set_sys_clock_khz` は
    放っておくと 48MHz へ落とす)。上げる前に XIP スイープを回すこと

- **D24. 実行権の貸し借りの単位は**クロック**にする** (2026-08-20 ユーザー指示:
  「cpu の実行時間譲渡は基準をクロックにしたほうがいい。オーバークロックの時
  適切に返すとは限らないし、見積もりのクロック数の方が望ましい」)。
  - 理由は 2 つあり、どちらも独立に成り立つ:
    1. **意味が動かない**。貸し手が縛りたいのは「どれだけ**仕事**をしてよいか」で、
       仕事はおおよそクロック数。µs で書くと、クロックを上げた瞬間に同じ数字が
       黙って倍の仕事を意味するようになる
    2. **換算が要らない**。SysTick が数えているのはクロックなので、µs で持つと
       装填のたびに `cycles_per_us` で割り戻すことになる。その clk_sys が
       **貸している最中に変わらない保証は無い** (D23 のオーバークロック、将来の
       周波数切替)。換算済みの期限は静かにずれ、予定どおりに返ってこない
  - ★**SLEEP は µs のまま**。あちらは壁時計 (「20ms 後に起こして」) であって仕事量
    ではない。**違う量なので単位を揃えてはいけない**
  - 実装: `grant_frame` が絶対期限 [µs] ではなく**残量 [クロック]** を持つ。
    `grant_charge()` が今の刻みで使ったぶんを**全段から**引き (内側が走っている間は
    外側の時間も減っているので、一番内側だけでは足りない)、`arm_timer()` が一番
    内側の残量をそのまま装填する。カーネルの貸し借り経路から `time_us()` と
    `cycles_per_us()` が消えた。実機: `grant: within the lent budget (=2056)`
    (300000 クロック = 150MHz で 2000µs 相当、誤差 2.8%)
  - ★**残量が少なすぎるときは貸さずに断る** (`GRANT_TOO_SMALL` →
    オブジェクト側は `NO_TIME`)。タイマの装填には下限があり (装填直後の発火は
    取りこぼす)、下限へ丸め上げて貸すと借り手は**貸された以上に走れる** —
    外側でクランプしている意味 (I-7) が消える。少ししか残っていないときに黙って
    多めに貸すより、断って呼び出し元に判断させるほうが正しい。
    判定は claim より**前**に置く (先に claim すると断るときに相手を READY へ
    戻す後始末が要り、戻し忘れると走れるスレッドが黙って消える)。
    スケジューラ側は `NO_TIME` を見たら候補探しをやめる — 自分の持ち分が尽きて
    いるのだから次を試しても同じ答えしか返らない (空回りしない)。
    ★なお**参照実装にこの規則は無い**。あるのは似て非なる 3 つ:
    `systick_arm_for` の 100 サイクル装填下限 (拒否ではなく丸め上げ)、
    `GRANT_RETRY_US = 50` (カーネルオブジェクト走行中は取り上げを延期)、
    そして**スタック側の headroom 検査** (残りが余裕未満なら呼び出しを拒否)。
    「バッファ未満なら渡せない」という形はスタック側にあり、時間側には無かった

- **D25. 他 ISA でのクロック基準の評価** (2026-08-20 ユーザー依頼: RISC-V (ESP32-C
  系) / x86_64 / Xtensa)。
  - ★評価の軸を 2 つに分ける。**混ぜると判断を誤る**:
    - **数える (charge)**: どれだけ仕事をしたか。**4 つとも専用のサイクルカウンタを
      持っている**ので、どこでも自然にできる
    - **期限で割り込む (arm)**: タイマが何を数えているかで決まる。ここが割れる

    | ISA | 数える | 期限で割り込む | 相性 |
    |---|---|---|---|
    | ARMv8-M (今) | SysTick / DWT CYCCNT | SysTick が**クロックを数える** → そのまま載る | ◎ |
    | Xtensa (ESP32/S3) | CCOUNT | **CCOMPARE が CCOUNT と比較** → そのまま載る。32bit なので SysTick の 24bit より広い | ◎ |
    | RISC-V (ESP32-C 系) | `mcycle` (Zicntr) | `mtimecmp` は **`mtime` (固定レート)** としか比較できない。サイクル比較レジスタは無い | △ |
    | x86_64 | PMU の `CPU_CLK_UNHALTED` | TSC-deadline は壁時計。**TSC は固定レートでサイクルではない** (invariant TSC)。サイクル期限は PMI が要る | ✕〜△ |

  - **RISC-V**: 仕様が「実時間カウンタ (`mtime`、固定レート)」と「サイクルカウンタ
    (`mcycle`、比較レジスタ無し)」を**意図的に分けている**。なのでクロック期限は
    直接は張れず、換算が要る。ただし**換算しても契約は守れる**: タイマは概算で
    (短めに倒して) 張り、発火時に `mcycle` を読んで**実際に使ったサイクルを引き**、
    残りがあれば張り直す。これは既に実装してある「24bit に収まらないぶんを刻んで
    継ぎ足す」パターンと**同じ形**なので、arch を差し替えるだけで済む。
    貸している最中に周波数が変わっても、charge が実測なので契約は収束する
    (代償はタイマ割り込みが増えること)。`Sscofpmf` (カウンタ溢れ割り込み) がある
    コアなら、サイクル期限を直接張ることもできる
  - **x86_64**: 皮肉なことに、**ユーザーの主張が一番強く効くのに実装が一番重い**。
    turbo / thermal / P-state で周波数が常時動くので「µs = 仕事量」が最も嘘になる。
    一方 TSC は**固定レートで動く** (名前に反してサイクルを数えていない) ので、
    本当のサイクル数は PMU の固定カウンタでしか取れず、そこに期限を張るには
    PMI (性能カウンタ割り込み) が要る。実用上は「TSC で概算して張り、PMU で
    実測して引く」= RISC-V と同じ形になる
  - **Xtensa**: むしろ ARMv8-M より素直。CCOMPARE が CCOUNT を直接比較するので
    刻んで継ぎ足す必要すら (32bit ぶんまでは) 無い
  - **結論**: **クロックを契約の単位にするのは 4 つとも正しい**。違うのは
    「タイマが何を数えているか」だけで、それは arch の実装詳細。
    ★そのために `arm_timer` / `grant_charge` の 2 つに分けてある —
    charge はどこでもサイクルカウンタから実測でき、arm だけが arch ごとに
    (そのまま載る / 換算して刻む) と変わる。**契約は移植可能で、変わるのは
    割り込みの回数だけ**
  - ★★**この評価で見つかった穴と、その決着**: サイクルカウンタは**コアが止まって
    いる間は数えない** (WFI / WFE / HLT)。x86 の `CPU_CLK_UNHALTED` は名前どおり、
    ARMv8-M の SysTick もプロセッサクロックを数えるので WFI で止まる (RP2350 で
    実際に止まる)。素直に読むと「借り手が眠ると予算を消費せず、取り上げも起きない」
    = 貸し手へ CPU が戻らない、という穴に見える。
    **決着 (2026-08-20 ユーザー判断)**: これは機構の穴ではなく**契約の話**として
    閉じている。「スリープに入ることはカーネルオブジェクトは分かっているし、その上に
    乗るシステムオブジェクトも分かった上でカーネルオブジェクトにスリープを要請する。
    契約の面では、スリープに入る段階で消費するリソースが存在しない、もしくは
    契約破棄が行える」。つまり**眠るのは要請であって、要請した時点で実行権は返る** —
    「眠りに入る = 契約の終了」。壁時計の非常口を機構側に足す必要はない
    (足すと、貸し借りの単位が 2 つになって「仕事量」という意味が濁る)
  - ★この決着は**確かめて初めて契約になる**ので、自己テストにした
    (`thread_ladder.cpp` の「借りたまま眠ろうとしたら契約はそこで終わる」)。
    実機: `sleep: the borrower gave the grant back (=1)` = EXPIRED(0) ではなく
    **YIELDED(1)** で返っている (機構が救ったのではない)。
    `sleep: the lender resumed at once (=39)` = 5000µs 貸して 50000µs 眠る相手
    なのに貸し手は 39µs で戻った

- **D26. オブジェクトシステムは定数時間で抜ける (文字列を持ち込まない)**
  (2026-08-21 ユーザー指示:「svc ハンドラ自体は定数時間で抜けるけど、基本的には
  カーネルオブジェクトも定数時間でハンドリングできる方が性能面では好ましい。
  つまり、オブジェクトシステムにおいて基本的には文字列処理はいれたくない」)。
  - 監査結果 (2026-08-21):
    - **配り口は定数**。`handle()` は密な整数の switch なので、コンパイラが
      テーブル分岐にする。逆アセンブルで確認: `cmp #15` + `tbb [pc, ip]` の 2 命令。
      番号が何であれ同じ命令数で抜ける
    - **オブジェクト / メソッドの解決も定数**。どちらも ID による配列添字で、
      **名前で引く API は 1 つも無い**。`grep` でオブジェクトシステム本体に
      文字列処理 (strcmp/strlen/memcmp/char*) がゼロであることを確認済み
    - `exit_method` / `call_method` / `export_method` / `create_object` /
      `current_object` / `caller_object` / `claimed_depth` / `set_budget` /
      `memory_owner` / `memory_hand_over` はすべて定数
    - ❌ **`arena_allocate` / `arena_release` が O(ブロック数)** だった。first-fit の
      線形探索と、併合のためのリスト全走査。**SPAWN と MEMORY_ALLOCATE の経路**なので
      直した (下記)
    - ⚠️ `schedule()` は O(THREAD_COUNT) の巡回。上界はあるが定数ではない。
      これは**方針**側なので急がないが、ready のビットマップ + ctz で定数にできる (未着手)
  - **arena を階級別空きリストへ書き換えた (O(1))**:
    - 大きさを 2 冪で階級に分け、階級ごとに空きを繋ぐ。要求に対しては
      「その階級のどれを取っても足りる」階級 (= **ceil** で取った階級) 以上から
      選ぶので、階級の中を歩かなくてよい (floor で取ると中を探すことになる)
    - **空き階級のビットマップ**で「要求以上で最小の空き階級」を ctz 1 発で引く
    - **境界タグ (`prev_bytes`)** で解放時に左隣を O(1) で見つける。旧実装が
      一番重かったのはここ (併合のためにリストを頭から歩いていた)
    - **双方向リスト**で、併合により消えるブロックを途中から O(1) で外す
    - 最上位階級が飽和するとそこだけ線形になるので、**arena がその大きさを
      超えないことを `arena_init` が検査する** (気をつけるでは守れない)
    - ★ヘッダに詰め物が要る: 貸す先頭 (ヘッダ直後) を 8B 境界に乗せないと、
      借りた側の LDRD/double が落ちる。`static_assert` が実際にこれを捕まえた
  - **「O(1) にした」は主張であって証拠ではない**ので、`memory_ladder.cpp` で
    実測する: 空きが 1 つの状態と、1 つおきに返して穴を空けた状態で、借り返し
    2000 回の時間を比べる。線形探索なら穴の数だけ伸びる
  - FS だけは例外で、`lookup` は名前の比較を伴う線形走査。ただし**返すのは
    アドレス**なので、引いた後の読み出しは純粋なメモリ参照 = 定数
    (D21 の「XIP 前提でアドレスを返す」がそのまま効いている)

- **D27. 名乗りはカーネルオブジェクトの暫定の宿。System Object が起動したら引き継ぐ**
  (2026-08-21 ユーザー判断:「system object が起動するまで、つまり今の段階での
  デバイスドライバオブジェクトなどについての管理は、名乗る機構をつけておく方が
  いいかな。で、システムオブジェクトが起動したときにカーネルオブジェクトから
  引き継ぐ形の方が好ましくはある」)。
  - **なぜ要るか — 今日の実測**。手で振ったオブジェクト番号の衝突が 1 日に 2 回起き、
    **2 回とも無音**だった:
    - flash_fs の `11` × 非特権プローブの `11` → 「非特権のはずが特権だった」という
      **別物の失敗**に化けた (計測が嘘をついた)
    - sleeper の `6` × blink の `6` → 揺らぎの計測が**黙って停止**した。それでも
      自己テストは `36 passed / 0 failed` のままだった
    どちらも `CREATE_OBJECT` は正しく `ALREADY_EXISTS` を返していた。**戻り値を
    見ない呼び出し側が居た**のが原因で、参照実装の `driver_streams.hpp` も同じ形の
    手書き登録表を持ち「そもそも衝突させないこと」と書いている = 気をつけることで
    守ろうとしている。守れない
  - **API の形**:
    - `DECLARE_NAME(name)` — オブジェクトが**自分で名乗る**。誰として登録するかは
      `EXPORT_METHOD` と同じく**発行元から導出**するので他人の名は騙れない。
      付け直しは断る (控えた名が別物を指すと、番号の衝突と同じ壊れ方になる)
    - `OBJECT_NAME(id)` — 名前を返す (0 = 無名)
  - **★★D26 との両立が設計の要**: カーネルオブジェクトは名前を**保持して返すだけ**で、
    **比較を一切しない**。比較 = 文字列処理を入れた瞬間にオブジェクトシステムが
    定数時間で抜けられなくなる。名前は**コピーもしない** (ポインタを持つだけ)。
    したがって `resolve(name) → id` はここには**作らない**
  - **引き継ぎ**: System Object が起動したら `OBJECT_NAME` で全部読み出して自分の
    索引を作り、以後 `resolve(name)` を提供する。**文字列処理はそちらに閉じる**。
    設計文書 §12.3 が md をカーネルオブジェクトに置いた理由は「解決の往復が
    呼び出し経路に乗るから」だが、**名前はその逆** — bind 時に一度引くだけで
    呼び出し経路には乗らないので、System Object でよい (§11.4「System Object は
    軸 C だけを持てばよい」とも噛み合う)
  - **今日いちばん効いた変更**: `create_object` が衝突時に
    `[KOBJ] object 15 is already taken by 'namer' — create refused` と**鳴る**。
    気づけるかどうかを呼び出し側の行儀に賭けない。自己テストでも
    「衝突が拒否されること」を確かめる (許可のテストだけでは証拠にならない)
  - 番号の配布は D28 で解決した (実行時ではなく**ビルド時**に振る)

- **D28. オブジェクト番号は**ビルドシステム**が振る (実行時の登録簿は作らない)**
  (2026-08-21 ユーザー判断:「ラジコンカーで文字列処理が必要なオブジェクトとか
  いらないというか、手振りできる環境ってあるわけだよね」→「ビルドシステムで

  - ★**解決策の階層を一段間違えていた**という自己訂正。今日の事故の原因は

    費用だけ払って何も買わない
  - **なぜ C++ の列挙ではなくビルドシステムか**: 列挙でも同一ヘッダ内の衝突は

    要る。**ビルドシステムはどのモジュールが入っているかを既に知っている**
    (`USE_SHIZUKU_MODULES`) ので、そこが消える。各モジュールは自分の名前を
    宣言するだけでよく、他モジュールのヘッダを見なくてよい —
    XNO を別リポジトリに分ける D17 とも噛み合う
  - 仕組み: 各コンポーネントが `objects.list` (1 行 1 名) を置き、
    `shizuku_declare_objects(<path>)` / Bazel の genrule がそれを渡す。
    **番号はソースのどこにも書かれない**。二重宣言と `SHIZUKU_OBJECT_COUNT` 超過は
    生成の時点で落ちる
  - ★**CMake と Bazel が同じスクリプト (`tools/gen_object_ids.py`) と同じ
    `objects.list` を使う**。番号を振る規則や名前の一覧を 2 つ持つと、片方だけ
    直して番号がずれる — 焼いたものが黙って別物になる類の壊れ方なので、
    二重に書く場所をどこにも作らない。入力の `.list` は**パス順に並べ替えてから**

- **D31. 消去は「本当に 1 へ戻すとき」だけ — 目録は追記式にする**
  (2026-08-21 ユーザー指摘:「なんでそんなに遅いの？フラッシュの限界なのか、それとも
  単純にアルゴリズムが悪いのか。erase コマンドとか実行してない？上書きでいいと
  思うんだけど」)。
  - **まず内訳を測った**。「遅い」だけでは媒体の限界か手順の問題かを言い分けられない:

    | | 合計 | 消去 | 書き込み |
    |---|---|---|---|
    | 旧実装 | 74,136 µs | 65,697 µs (**2 回**、89%) | 7,838 µs |

    1 セクタ (4KB) の消去が **約 33 ms**。これは W25Q の物理的な限界 (typ 45ms なので
    むしろ速い側) なので**媒体を責める話ではない**。問題は**消去を 2 回している**こと
    だった: (a) 中身のセクタ (b) 目録セクタ
  - **NOR は書き込みが 1→0 しかしない**。消去が 0xFF に戻す操作で、書き込みは
    ビットを落とすだけ。したがって:
    - **まだ 0xFF の場所へは消さずに書ける**
    - 状態の遷移も「ビットを落とす向き」なら消さずに書ける
  - **直したもの**:
    - **目録を追記式に**。枠 0 に名乗り、以降は空き枠へ**追記**する。書き換えない
    - **置き場所の先頭 (bump) を持たない**。項目から導出する — 持つと store のたびに
      書き換えが要り、書き換えには消去が要る。**これが 2 回目の消去の正体**だった
    - **削除は state のビットを落とすだけ** (LIVE → DEAD)。0xFF へ戻さないので消去不要
    - 1 枠の追記は、その枠を含む 256 バイトのページを書く。**同じページの他の枠には
      0xFF を書く** — 0xFF はビットを 1 つも落とさないので隣は変わらない
    - **置くときに `is_blank()` で見て、要るときだけ消す** (遅延消去)。読むのは XIP
      なのでただのメモリ走査で、消去 33ms に比べれば無視できる
    - FORMAT は中身のセクタを消さない (1MB ぶんで 8 秒以上かかる)。目録 1 セクタだけ
  - **★実測 (2026-08-21)**:

    | | 合計 | 消去 | 書き込み |
    |---|---|---|---|
    | 旧実装 | 74,136 µs | 65,697 µs ×2 | 7,838 µs |
    | 新・消去が要る場所 | 35,406 µs | 33,667 µs ×1 | 1,107 µs |
    | 新・定常状態 (0xFF の場所) | **2,587 µs** | **0** | 1,648 µs |

    **29 倍**。残っているのはページ書き込み 3 回 (中身 + 古い項目を殺す + 新項目) で、
    消去はゼロ。再起動をまたいで残ることも確認済み
  - ★**途中で一度しくじった**: probe が毎回 FORMAT していたせいで行き先が前回使った
    セクタへ巻き戻り、追記式にしたのに毎回 33ms の消去が復活していた。
    **前へ進み続ける**形 (空きが尽きたときだけ FORMAT) にして初めて効果が出た。
    追記式は「巻き戻さない」とセットでないと意味が無い
  - **残り**: `flash_write` がページごとに他コアを止め直している (1 回の store で
    3 回)。論理的な 1 操作につき 1 回にまとめられる (未着手)

- **D34. 締切のある系で flash を使うなら、消去は「走行中の経路」に置けない**
  (2026-08-21 ユーザー提起:「リングバッファって flash が足りなくなった時に起こる
  ワイプが遅い説の話ね。これが 10ms を超えると飛行ロボコンとかではまずい」)。
  - ★**私が最初に取り違えた**。ユーザーの懸念は「読んでいる最中の上書き」ではなく
    **「尽きたときの消去が締切を壊す」**のほうだった。D33 の seqlock は別の問題の
    答えで、こちらの答えにはならない
  - **実測 (2026-08-21)**:

    | 消去単位 | 実測 | 4KiB あたり |
    |---|---|---|
    | 4 KiB (セクタ消去) | 32,967 µs | **32,967 µs** |
    | 64 KiB (64KB 境界に揃えたブロック消去) | 78,994 µs | **4,937 µs** |

  - ★★**64KB 境界に揃っていないとブロック消去にならない**。ROM が `0xD8` へ
    切り替わるのは範囲が境界に乗っているときだけで、途中から始まる 64KB は全部
    セクタ消去になる。**最初これを揃えずに測って「ブロック消去にしても速くならない」
    と読み違えかけた** (揃えない 64KB は 510,557 µs = 31,909 µs/4KiB だった)
  - **結論**:
    1. **1 セクタの消去 33ms は縮まらない** — 媒体の性質。走行中に 1 回でも消したら
       10ms の予算は必ず壊れる。**消去を書き込みの経路に置かない**以外に道は無い
    2. `PREPARE` (先に空けておく) を足した。**費用は消えないが、いつ払うかを選べる**。
       離陸前・整備時にまとめて払っておけば、走行中の書き込みは「まだ 0xFF の場所へ

- **D35. ストリーム — 制御はメソッド、データはライブラリ。運ぶものは用途で変える**
  (2026-08-21 ユーザー指示:「stream を実装して、flash FS の read/write は stream
  経由で行われるようにしようか」「flash fs は別にドライバ内部の読み出しとかは DMA
  でもいいんじゃね。**MPU 保護下にある非特権オブジェクトからも read/write したい
  だろ**。ioctl とかの代わりとしてメソッド呼び出しが残る分には構わんが」)。
  - **柱 1: 制御プレーンとデータプレーンを分ける**。create/open/bind は svc、
    push/pop は **svc を通らないライブラリ**。単一アドレス空間で push/pop を svc 化
    しても保護は 1bit も増えず、1 レコードあたり 100 サイクル以上の体裁代を払うだけ。
    開け閉めは制御なのでメソッド呼び出しのまま (= ioctl 相当)
  - **柱 2: 何を運ぶかは用途で変える**。★flash の読みを「バイトの流れ」にしては
    いけない — あれは XIP で**アドレスをそのまま返せる**のが取り柄 (D21) で、
    バイトに直した瞬間にその取り柄が消える:
    - **読み**は `extent` (XIP アドレス + 長さ) を運ぶ。**1 バイトも写さない**
    - **書き**はバイトを運ぶ。締切のある側が flash の 33ms を待たされないための
      緩衝がまさに要るところで、そこは写す価値がある (D34)
  - **柱 3: SPSC を機構で強制する**。席は 1 つずつしか無く、二人目は `SEAT_TAKEN` で
    断られる。★参照実装の「直接ハンドル型」は登録を通らないので席の強制が効かず、
    コメント自身が「役割は規約で守ること」と書いていた — それは守れない形なので
    持ち込まない。番号もカーネルオブジェクトが割り当てる (呼ぶ側に選ばせると
    オブジェクト番号で 2 回踏んだのと同じ衝突が起きる。D28)
  - **★非特権から読み書きできることが要点**。そのために:
    - ストリームの実体を**オブジェクト arena** (非特権から届く側) から借りる。
      静的領域に置くと region の外 = 特権のみになり、非特権が push できない
    - 読みは XIP を直接読ませる。region0 が読み出しを全員に許しているので、
      **非特権のまま写さずに読める**
    - 書きは非特権ではフラッシュを焼けないので、バイトをストリームへ流し、
      特権側の書き手が汲んで焼く
  - **実機の証拠 (2026-08-21、2 コア、72 passed / 0 failed)**:
    - ストリーム単体: `cores seen 0x3` / 4000 レコード / **欠落 0 / 順序入れ替わり 0** /
      押し戻し 26 回 (容量を 64 に絞って必ず満杯に出会わせた) / 2 人目は拒否
    - flash 越し: `the unprivileged writer ran non-privileged (=15)` →

    (非特権が読める側)**。`pop` が書き換えるのは `rd` だけで、それは RAM 側にある。
    この 2 つの置き分けが「非特権が読める」の正体
  - 実機: `the file itself is the stream (=300)` — 300 バイトのファイルが
    そのまま 300 レコードのストリームになる。RAM の環は 1 つも要らない

- **D37. ストリームの接続は DMA で直結する (中継オブジェクトを消す)**
  (2026-08-21 ユーザー指示:「DMA ポンプもやっておく必要があるだろうね」)。
  - `STREAM_CONNECT(src, dst)` が src の consumer 席と dst の producer 席を占め、
    DMA チャネルを 1 本握って両者を直結する。以後 src へ流れたものは
    **「中継オブジェクトが pop して push する」段を通らずに** dst へ届く
  - ★**DMA チャネルはオブジェクトへ渡さない**。DMA は MPU を素通りするので、
    渡した瞬間に非特権オブジェクトが任意の番地を読み書きできる。要求だけ受け付ける
  - ★席を接続が占めるので、**手押しとの二重供給を機構で防げる**
    (`a hand-fed producer is refused on a joined stream` で確認)
  - ★レコードの大きさが違うものは繋がない。詰め替えは「変換」であって「接続」では
    ないので、要るなら中継オブジェクトを書くべき (黙って詰め替えない)
  - ポンプは `schedule()` から回す。接続 0 本なら数語読んで即戻るので、専用スレッドを
    持たない (専用スレッドはそれ自体が予算を食う口になる)。両コアが同時に回さない
    よう try-lock で、**取れなければ待たずに諦める** (次の周回で回る)
  - **実機の証拠**: XIP を実体とする読みストリーム → DMA → 非特権の受け手の環。
    `every byte arrived through DMA (=300)` / `the bytes are the ones in flash
    (=37442)`。**CPU は 1 バイトも写していない**し、中継オブジェクトも居ない

- **Q8. flash を好き勝手読める件は、API ではなく MPU の配置の問題**
  (2026-08-21 ユーザー懸念:「ユーザーランド API に頼ってるとはいえ、flash を
  好き勝手読ませるのは正直いうと微妙な気はする」)。
  - ★懸念は正しいが、**原因はストリーム API ではない**。今の `protection_init` は
    region0 に **XIP 全域を `ACCESS_RO_ALL`** で張っている。つまり非特権オブジェクトは
    API を使わなくても、ポインタを計算するだけでフラッシュ全域 (他のファイルも
    ファームのコードも) を読める。**API を絞っても何も変わらない**
  - したがって今の読み API は **capability ではなく便宜**。そう呼ばないこと
  - 直す場所は §11.3 の**オブジェクトごとの region 切り替え** (CALL で特権を
    差し替えるついでに region set も差し替える)。PMSAv8 の region は base + limit
    なので、**セクタ境界に揃ったファイルの extent はちょうど 1 region に収まる**
  - ★**API の形は変えなくてよい**。ディスクリプタは既に base + capacity を持って
    いて、それがそのまま「渡した権限」になっている。region が per-object になった
    瞬間に、同じディスクリプタが本物の capability になる
  - **実装した (D44, 2026-08-24)**。ただし `call_request` に載る値のスコープが
    「対象オブジェクトの性質」であって「呼び出し元が指定する引数」ではないので、
    最初の想定と少し違う形になった。詳細は D44。

- **D40. プローブは要らないかもしれない — M33 の自己ホスト型デバッグ**

      `MON_PEND` / `MON_REQ`

      なので `FP_CTRL.NUM_CODE` を**実行時に読んで**決めること
    - **DWT** (`DWT_COMP*` / `DWT_FUNCTION*`) — ウォッチポイント

    デバッガが書ける。外付けのプローブが要らない
  - ★**この設計と相性が良い理由**: halting debug はコアを丸ごと止めるが、
    DebugMonitor は**優先度が設定できる普通の例外**。だから
    「ブレークポイントで**そのスレッドだけ**止め、他は走り続ける」ができる —
    I-9 (1 つの誤りで系を落とさない) とまっすぐ噛み合う
  - ホストとの経路は**既にある USB CDC** でよい。GDB のリモートプロトコルを喋る
    stub をオブジェクトとして書けば、`arm-none-eabi-gdb` から
    `target remote /dev/cu.usbmodem*` で繋がる → **launch.json と F5 の流れは
    プローブ版とまったく同じまま、プローブが要らなくなる**
  - **正直な制約**:
    - halting debugger が繋がっている間は `MON_EN` が効かない (`C_DEBUGEN` が勝つ)。
      両方は同時に使えない
    - DebugMon ハンドラ自身と、それより優先度の高いところは踏めない
    - flash は書けないので、ブレークポイントは `BKPT` の埋め込みではなく **FPB**
      で置く必要がある (数に限りがある)
    - 錠を握ったスレッドで止めると相手のコアが進めないのは halting debug と同じ
  - **未着手**。やるなら「DebugMon ハンドラ + FPB/DWT の面倒を見るオブジェクト +
    CDC 上の GDB stub」の 3 点で、規模はストリーム 1 本ぶんくらい

    - `KERNEL::debug_dispatch` — 記録して**そのスレッドだけ止め**、他へ渡す
    - `KERNEL::suspend/resume` — `TERMINATED` と違い**文脈は生きたまま**なので、
      レジスタを見て書き換えてから再開できる

  - **実機で確かめた (自己テスト、93 passed / 0 failed)**:
    ハードウェアブレークポイント **8 個** (FP_CTRL から実行時に読んだ値)、
    命中 → **対象スレッドだけ SUSPENDED**、**他は走り続ける**、再開すると続きから、
    1 命令実行も動く
  - ★★**2 つの罠を踏んだ。どちらも「事象は起きているのに嘘の観測が出る」形**:
    - **DEMCR に書いたら dsb + isb が要る**。入れないと「次の命令」ではなく数命令
      あとで止まり、狙った場所と違うところで止まる
    - **例外ハンドラが書く記録を素直に読むとコンパイラがレジスタに載せたまま**に

  - **GDB stub (USB CDC 越し、プローブ不要) — 動くところ**:

    変数の表示 (`print g_debuggee_rounds` → 実値)
  - **★動かないところ (未解決)**: 2 回目以降の `continue` と `stepi` が

    **通り道 (CDC の共有) が原因と見ている**
  - **原因は診断出力との相乗り**。GDB が繋いだ瞬間も `[STRESS]` が流れており、

  - stub の入出力は `read_byte` / `write_byte` の 2 つに閉じ込めてあるので、

  - **実装した**。pico_stdio_usb は CDC 1 本前提で記述子も weak ではないため、

  - ★診断の出力は**溢れたら捨てる**。相手が読んでいないときに詰まると系が止まる —

  - ★**stub は自分自身を止めてはいけない**。`do_continue` が「止まったスレッド」へ

  - ★**CDC を分けて消えるのは「診断が死ぬ」ほうだけ**。stub が固まれば GDB の
    channel は当然死ぬが、診断が生きていれば**何が起きたか見える**し、焼き直しも

- **D43. 「2 回目以降の continue/stepi が固まる」— 3 回目でようやく当たった原因**
  (2026-08-24 実装。D41/D42 の誤診 2 回を受けて、ユーザーが「推測せず証拠から」と
  明記して依頼)。
  - ★★**推測をやめて `set debug remote 1` の生ログを取ったら 1 発で見えた**。
    `debug_dispatch` に一時的な診断出力を仕込んで実測すると:
    - 1 回目のブレークポイント (continue) → `thread=3` (debuggee, 正しい)
    - 2 回目 (continue の「ブレークポイントをまたぐ内部 step」= stepi と同型) →
      `thread=4`。これは **stub 自身のスレッド**だった
  - **本当の原因**: `DEMCR.MON_STEP` は「対象スレッドが次に走ったとき」ではなく
    **arm した瞬間に実行中の文脈の、次の 1 命令**に対して発火する。旧実装は
    stub 自身のスレッドの中で `ARCH::debug_step(true)` を呼んでから
    `resume(target)` していたので、次の 1 命令は**stub 自身の後続命令**であり
    target のものではなかった。do_continue には自己停止ガードがあるが
    do_step には無かったため、stub がそのまま SUSPENDED になり、GDB channel が
    永久に無応答になっていた。D41/D42 の「診断の混入」「CDC 共有」はどちらも
    無罪 — 単に別の壊れ方を先に踏んで、それを直したら症状が残っただけだった。
  - ★一度棄却した仮説: 「MON_STEP はコア単位、target が別コアへ逃げる」説。
    debuggee/stub を両方 core0 に固定して実機で再現したが**症状は変わらなかった**
    ので棄却した。棄却しても記録するのは、同じ仮説を後で誰かがまた立てないため。
  - **直し方**: MON_STEP を stub の通常コードから直接 arm するのをやめ、
    「次の 1 命令が確実に target のものになる場所」= 例外復帰の直前
    (`CTX_RESTORE`) で arm する。
    - `KERNEL::arm_step(thread)` — 予約するだけ (`m_step_target` へ CAS 対象を書く)
    - `KERNEL::consume_pending_step()` — **あらゆる復帰経路** (SVC/PendSV/
      DebugMon/Fault のどれでも) の `CTX_RESTORE` 先頭から毎回呼ばれる。
      復帰しようとしている文脈がちょうど予約した相手なら、ここで初めて
      `ARCH::debug_step(true)` を立てる。対象でなければ何もしない
    - これでコアも意識しなくてよくなった (どのコアが実際に target を復帰させても、
      **そのコア自身が**正しく arm する) — D43 棄却仮説の cross-core 対策も
      副産物として要らなくなった
  - ★★**修正作業中に実機を 1 回沈めた**。`CTX_RESTORE` は SVC/PendSV/DebugMon/
    Fault 全部が通る**系で一番熱い経路**なので、ここに挟むフックにバグがあると
    起動のごく初期 (GDB 接続すら要らない) で全系が固まる。実際に固まり、
    診断も GDB も USB リセット要求 (`picotool reboot -f`) にも応答しなくなった。

    - agent → 自コアの FPB を誰も面倒見なくなり、以後ブレークポイントの
      置き直しが効かない。しかも `wait_for_agents()` が毎回 10 万回空回り
      してから諦めるので、Z パケットのたびに待たされる
    - server → GDB チャネルごと無応答 (系は生きたまま = 一番分かりにくい)
  - **守り方は「止める要求を弾く」ではなく「一覧に出さない」**。出さなければ
    `H` も `vCont` も掴めない (どちらも `thread_is_listable` を通す) ので
    入口が 1 つで済む。デバッガ自身は**被デバッグ対象ではない**という筋にも合う。
  - ★**表を 2 つ持たない**。転送スレッド用に `g_protected_threads` が既に
    あったので、自前のマスクを作らずそこへ寄せた (2 つあると必ず片方だけ
    更新する日が来る)。`monitor list` は保護対象も**見せた上で**
    `[transport: 止められない]` と印を付ける — 見えるが掴めない、が正しい形。
  - ★**登録は spawn した側で**行う。agent 自身に名乗らせると、起き上がるまでの
    間だけ一覧に出て止められる窓ができる。spawn の戻り値なら走り出す前に閉じられる。
  - ★★実測で 1 つ雑な挙動を見つけて直した: **保護対象を名指しすると、代わりに
    既定の相手が止まっていた** (`vCont;t:9` で blink が止まった)。名指しが
    解決できないときは**何もしない** — 頼まれていないものを黙って止めるのは、
    無音で別のことをするのと同じ。
  - **実機で確認**: GDB の一覧が 11 本 → **8 本**に減り `gdbserver`/`gdbagent`
    が消えた。それらを名指しで止めにいっても stub は生きたまま
    (`qfThreadInfo` が答え、`Z0` も通る = agent が生きている)。
    正当な相手は今まで通り止まる。all-stop の連続命中 3/3、
    `selftest=97 passed/0 failed` も不変。
  - ★★★**本来これは System Object が持つべき制約** (誰が誰を止めてよいか)
    であって、stub が自前の表で守るのは繋ぎ。資源の階層が入ったらそちらへ移す。

- **D57. 「止めたのに走り続ける」の残り半分 — 寝ているスレッドは締切で勝手に起きていた**
  (2026-08-26。D54 の続き。XNO 側で「カーネルの停止がまだ効いていない」と報告が上がり、
  こちらで BLE 越しに再現させたところ**フル速度のまま**だった)
  - **症状**: `monitor target <n>` で SUSPENDED にした `bno055` の周回カウンタが
    **+88/8秒 → +89/8秒**と**まったく減速しなかった**。同じファームの `blink` は
    止まっていたので、「suspend が効かない」ではなく**相手による**、が最初の手掛かり。
  - **なぜ Shizuku では再現しなかったか**: 試験ファームには常時 READY な負荷スレッドが
    3 本居る。だから止めた側は**必ず CPU を手放す**。XNO は 13 本ほぼ全部が寝ているので
    `schedule()` が候補を見つけられず、**手放さないまま**回り続けていた。
    ★**再現しない現象は「直った」ではなく「条件が違う」**。負荷の有無だけで
      挙動が反転するので、この種の確認は**寝ているだけの系**でも回すこと。
  - **本当の穴**: `KERNEL_OBJECT::sleep_us` のループが**締切だけ**を見ていた。
    `suspend()` が保証するのは「**次に選ばれない**」ことだけで、**既に CPU を
    持っている相手には効かない**。だから止められていても締切が来れば素通りし、
    そのままユーザコードへ戻っていた。**カーネルの状態は正しく SUSPENDED だった** —
    実測で 12 秒間 210 サンプル全部 SUSPENDED、なのに走っていた。
  - **直し方 (方針側 = kobj)**: ループの抜け条件に状態を足しただけ。
    ```cpp
    while ((int64_t)(deadline - time_us()) > 0 ||
           kernel_instance.thread_state(self) == state_t::SUSPENDED) { ... }
    ```
    ★**あらゆる例外復帰に検査を足す (CTX_RESTORE) 案は採らなかった**。系で一番熱い
      経路に毎回分岐が乗るうえ、以前試したときは**ゼロまで落ちなかった** (471 → 319 周)。
      「寝るとはどういうことか」を決めているのは kobj なので、**譲る場所で見る方が
      安くて正確**。カーネルは状態を持つだけ、という分業にも合う。
  - **残る限界 (正直に書く)**: これで止まるのは**どこかで譲るスレッド**だけ。
    `sleep_us` も `call` もしない純粋な計算ループは、今でも量 (budget) が切れるまで
    止まらない。また止められている間は `schedule()` を回し続けるので、
    **他に READY が居ないと空回りで熱い** — ここは Q7 (idle スレッド) が埋める穴。
  - **実機確認 (XNO, BLE 越し)**: `bno055` を止める → 周回カウンタ
    **+80/8秒 → +0 (16 秒間まったく進まず)** → 戻すと **+81/8秒**。
    他スレッド (blink/logger/ota/telemetry/flight_controller/bme280) を止めても
    bno055 は **+30/3秒**のまま = 止まるのは名指しした 1 本だけ。
    Shizuku 側は `selftest=97 passed/0 failed`、`thermal sampler` も 20 秒 +0 で不変。
  - ★★**計測でしくじった話を残す**: 途中 2 回、修正後のはずなのに「走り続ける」と
    出た。原因は**盤上のファームが自分のビルドではなかった**こと (別エージェントが
    同じボードを焼いており、スレッド表に `loadprobe` が増えて**番号が全部ずれていた** —
    `12` は `bno055` ではなく `flight_controller` になっていた)。
    **教訓**: 共有ボードでは (1) 実機のフラッシュから**命令列を読み戻して**
    手元の ELF と突き合わせる、(2) スレッド番号は**毎回引き直す** (`qThreadExtraInfo`)。
    どちらも 1 往復で済む。番号を覚えていると、黙って別のスレッドを測る。

## 3. 未決事項 (着手時にユーザー確認 or 暫定判断)

- **Q1. svc 番号の渡し方** (PORT §2.1/§8-2): 即値ハイブリッド維持か、レジスタ統一か。
  RISC-V (`ecall` に即値なし) を見据えるとレジスタ統一が共通化しやすい。
  **暫定推奨: 新 ABI はレジスタ渡しに統一** (即値は ARM 向け最適化として後日計測してから)。
  ただし未計測なので一方向ドアにしない (ABI 定数は 1 ヘッダに集約)。
- **Q3. スタック上限の縮退** (PORT §8-3): PSPLIM が無い ISA (ARMv7-M/RISC-V) での
  ソフト検査方式。ARMv8-M だけの間は `arch::stack_limit_set` の意味論だけ決めておく。
- **Q4. `latest_ver_from_flight_robocon/` を git に入れるか**。少なくとも docs 2 本は
  参照価値が高い。ビルド対象からは常に除外。
- **Q5. サブカーネル活性化中も PendSV 切替延期の対象にするか** (PORT §3.4 末尾の残課題)。
- **Q7. idle スレッドをどうするか** (2026-08-21 ユーザー提起)。実は
  `sleep_us` の「誰も居なければ締切まで空回りする」と**同じ問題**で、要る道具は
  1 つ = 「T まで何もすることがない」。
  - idle は**スレッドのまま**にすべき (D18 でスレッドはオブジェクトランドの資源に
    なったので、いつ寝るかは kobj の方針。カーネルに書くと方針が戻る)
  - 引っかかるのは**起こし方**。WFI するとサイクルカウンタが止まる (idle にとっては
    正しい — 仕事をしていないので) が、今の系に「T に起こして」という機構が無い。
    SysTick は貸し借り専用で、貸していないときは止まっている
  - 選択肢: (a) board のアラームをもう 1 本使う (b) grant のタイマを貸し借り以外
    にも使えるようにする。(b) は貸し借りの機構の意味を広げる話なので要判断
  - マルチコアだとコアごとに 1 本要る (affinity で固定)

- **Q6. 現行 configs の型注入変数の粒度**。OBJECT 系 (THREAD_TABLE/METHOD_TABLE/
  MEMORY_TABLE) は D1 によりカーネルから消え、kobj 側の構成になる。kit 変数の
  置き直しが必要 (`SHIZUKU_ARCH` / `SHIZUKU_BOARD` / `SHIZUKU_KOBJ_*`)。

## 3.5 ビルドシステムと言語の再検討 (2026-08-19)

ユーザー指示「CMake か Bazel かは検討し直せ (Bazel の方がおそらく望ましい)。
Rust も同様に検討 (こちらは事実上 Cargo 強制なので考える要素が多い)」を受けた再検討。

### ビルドシステム → **Bazel に決定 (D15)**

PORT §5.5 の一般論 (差分ビルド 0.88s / 再現性 / 構成=target / toolchain rule) に加えて、
このマシンで確認した決定打:

- **pico-sdk 2.2.0 (手元の `~/.pico-sdk/sdk/2.2.0`) は公式 Bazel サポートを同梱**している。
  `MODULE.bazel` / `bazel/toolchain` (mac-aarch64-rp2350 含む) / `bazel/platform` /
  `bazel/config` (PICO_BOARD 等の build setting) / UF2 生成 aspect
  (`@pico-sdk//tools:uf2_aspect.bzl`)。PORT 執筆時に最大の懸念だった
  「C 資産 (pico-sdk/tinyusb/btstack) を Bazel に載せる手間」が公式に解決済み
- ローカルに bazel 9.2.0 / bazelisk 導入済み (`/opt/homebrew/bin`)
- 使い方の要点 (bazel/README.md より):
  `bazel_dep(name="pico-sdk", ...)` + `register_toolchains(@pico-sdk//bazel/toolchain:mac-aarch64-rp2350)` +
  `--platforms=@pico-sdk//bazel/platform:rp2350`。ボードは
  `--@pico-sdk//bazel/config:PICO_BOARD=pico2`
- 残リスク: SDK の Bazel ビルドは CMake 側より新しく、btstack/cyw43 系の網羅性は
  CMake に劣る可能性がある。**ただしそれらは XNO (D17) 側の話**で、Shizuku 本体
  (kernel/kobj/arch/board 最小) には効かない。bring-up はカーネル最小構成で行う
- CMake の扱い: Bazel で「configure → ビルド → UF2 → 実機で svc 往復」が通るまで
  並存。通ったら CMake / cmake-kits.json を削除 (二重管理は D15 の趣旨に反する)
- configs 機構の写像: kit のキャッシュ変数 → Bazel の `string_flag`/`label_flag`
  (bazel/config パッケージを作る)。config.hpp 生成は `expand_template` で同形にできる。
  「モジュールが config_need_headers を積む」は provider か単純に
  ラベルリストの flag で表現する

### 言語 → **カーネルコアは C++ 維持、Rust は XNO 側の将来オプション (D16)**

PORT §5.6 の 4 理由を再点検した結論。ユーザーの指摘どおり Rust の考慮点は
「言語の質」ではなく**ビルド編成**にある:

1. **Rust は事実上 Cargo 強制** (ユーザー認識と一致)。`rules_rust`/`crate_universe` は
   内部で cargo を回して lockfile を解決するし、組込み `no_std` の `core`/`alloc`
   再ビルド (`-Z build-std`) は nightly + cargo 前提。Bazel を D15 で選んだ以上、
   Rust をコアに入れる = **ビルドシステム 2 つを一番痛い継ぎ目 (カーネル/SDK 境界) で
   接ぐ**ことになる。これが最大の反対理由で、PORT 執筆時から状況は変わっていない
2. カーネルの最難関 (例外フレーム幾何 / naked asm シム / xPSR bit9) は Rust でも
   `unsafe` の中に残り、型システムの守備範囲外 (PORT §5.6 理由 2 の実バグ 3 件)
3. 実機で検証済みの C++ 資産 (フレーム幾何・CTX_SAVE/RESTORE) を書き直すコストは
   高く、逆方向 (後から Rust オブジェクトを足す) は安い — 片方向にしか安くない
4. **Rust が本当に効くのは XNO 側** (ドライバ・アプリ: 所有権/ライフタイムが仕事を
   する層)。D17 の分離により「XNO の一部を Rust + Cargo (または rules_rust) で書き、
   安定 ABI 越しに Shizuku とリンクする」実験が Shizuku 本体を汚さずにできる。
   その将来のために ABI 境界に C++ 型を露出させない (D16)

再訪条件: (a) rules_rust の no_std/build-std 対応が cargo 非依存になった場合、
(b) XNO 側で Rust ドライバが実績を積み、コアへ広げる動機が実測で出た場合。

## 3.6 REDISPATCH 廃止の決定 (2026-08-19, ユーザー提起)

ユーザー指摘「結局ネスト数を引き渡すから REDISPATCH 要らなくない?」を受けた再検討。
**結論: プリミティブとしての REDISPATCH は削除する** (D3/D4/D5 を上のとおり改定)。
DESIGN §7.2-7.3 / PORT §4.6 は「REDISPATCH + CALL の 2 種」としていたが、これを
さらに 1 種 (CALL) に畳む。

**★誤読注意 (ユーザー確認済み 2026-08-19): 「svc のオブジェクトランドハンドリング
(サブカーネル化)」という機能は廃止しない。** 消えるのは専用プリミティブだけで、
機能は「kobj のルート表 (svc 番号範囲 → 担当オブジェクト) + CALL_STRICT(arg0=svc
番号, r1-r3=元引数, caller_cookie=元発行元)」として維持する。委譲先は naked shim
でなく普通の export メソッドになる (書きやすくなる方向の変更)。

### §3.6.1 svc ハンドラは 2 つある。混同しないこと (2026-08-19 確定)

**★2026-08-19 追記 (ユーザー指摘による修正)**: 当初この節で「カーネルが
カーネルオブジェクトの cookie を持って比較する」と書いたが、それも不要だった。
経路判定に使えるのは**カーネル自身が積んだ呼び出しフレーム**で、そこに
「ハンドラを起こすために積んだ枠か」を記録すれば足りる (書けるのはカーネルだけ
なので偽装不能)。したがってカーネルは cookie も identity も信頼ビットも持たない。
また「活性化 (activation) に権限が付く」という概念も置かない — 参照実装の
`in_handler` はその形で、ハンドラから呼ばれた先まで特権化する穴だった。
なお「カーネルオブジェクトのルータを例外文脈で C++ 直呼びする」案も検討したが
**却下** (ユーザー判断)。ハンドラはスレッドモードで走る。

「カーネルだけで svc dispatch は完結すべきでは / kobj を経由する必要があるのか」
というユーザーの問いに対し、**リファレンス実装の形が正しい**と確定した。

**★用語 (ここを混ぜると設計が壊れる)**:

| | カーネルの svc ハンドラ | オブジェクトランドの svc ハンドラ |
|---|---|---|
| 実体 | `KERNEL::svc_dispatch` (参照: `svc_cpp_handler`) | SET_HANDLER で登録するメソッド (参照: `kernel_obj_svc_handler`) |
| 走る場所 | 例外文脈 (Handler モード) | **スレッドモード** (呼ばれた側として) |
| 役割 | 機構。経路を決めてプリミティブを実行する | 方針。番号を解釈して担当へ配る |
| 番号の知識 | **持たない** | 持つ (それが仕事) |

- **カーネルが持つのは登録された entry 1 個** (`{ entry_pc, cookie, protection }`)。
  参照実装の `cpu_manager::svc_handler_descriptor` と同型。**番号 → ハンドラの表は
  カーネルに置かない** (置くと I-1 違反 + 方針がカーネルに入る)
- 信頼された活性化の svc → プリミティブを直接実行し、**カーネルの svc ハンドラ内で
  完結**する (オブジェクトランドのハンドラは経由しない)
- それ以外の svc → **登録済みのオブジェクトランドのハンドラをメソッドとして呼ぶ**。
  トランポリンは特別な機構ではなく、CALL と同じ「保護されたサブルーチン呼び出し」の
  一形態。実装でも `do_call()` 1 本を共有させ、これが分岐しないことをコードで担保する
- 番号での振り分け (サブカーネルへの委譲) はオブジェクトランド側の仕事。
  カーネルは番号の意味を持たない
- **したがってカーネルの語彙に「未知の番号」は存在しない**: 信頼された活性化しか
  プリミティブ選択に到達せず、そこで番号が引けないのは**カーネル自身の不変条件の
  破れ**なので panic する (参照実装と同じ)。信頼されていない活性化の svc は番号を
  見られることなく渡されるので、そもそも「未知」の判定が起きない。
  同様に「権限がない」も存在しない — 経路そのものが I-2 を強制する

**なぜハンドラをスレッドモードで走らせる必要があるか** (例外ハンドラ内で直接呼べば
1 回の例外で済むのでは、への回答。3 つとも回避不能):

1. **ARMv8-M の Handler モードは常に特権**。CONTROL.nPRIV は Thread モードにしか
   効かないので、例外ハンドラ内でサブカーネルを走らせると、ルート表に登録された
   だけのオブジェクトが全特権を得る = I-8 の否定であり、参照実装が削除した
   `SET_SVC_HANDLER` 乗っ取りの穴そのもの
2. **Handler モードからは svc を撃てない** (同優先度で HardFault へエスカレート)。
   ハンドラが CALL / RETURN を撃てなくなる
3. **スタックが MSP になる**。オブジェクト由来の処理が共有例外スタックを食うので、
   深い再帰が系全体を落とす (§8.1 の「消費したスレッドだけを止める」が崩れる)

参照実装で REDISPATCH_SVC が METHOD_CALL に対して持っていた優位と、その帰結:

| 参照実装での優位 | 新設計では |
|---|---|
| identity が潰れない (METHOD_CALL は kobj に化けた) | caller_cookie で CALL 側が獲得 → 差なし |
| 元 syscall の r0-r3 が潰れない | CALL は引数明示。番号 (r0 予約) + 実引数 r1-r3 = 4 スロットで収まる → 差なし |
| in_handler=1 で戻り経路にプリミティブが撃てる | **ネスト数申告 + 両側チェックで戻れる** (ユーザー指摘の核心)。そもそも I-8 でハンドラ特権は廃止済み → 差なし |
| カーネルが退避フレームから元引数を復元 (転送ミス防止) | 転送するのは信頼境界内の kobj のみ。identity e2e 自己テストが同じ網で捕まえる → 自己テストで代替 |
| REPLACE モード (exit, DESIGN §9.4) | `RETURN(n=2, depth_claim)` で同値 (PORT §4.5 の退避策)。+1 は kobj の 1 ヶ所に閉じ、I-6 的にも kobj が自分の積んだ 2 枚を落とすだけなので綺麗 |

副次効果 (すべて簡素化方向):
- サブハンドラ用 naked shim が不要になる (委譲先は普通の export メソッド)。
  shim が要るのはカーネル→kobj のトランポリン 1 ヶ所だけになり、
  「shim 自作は必ず間違える」地雷の面積が縮む
- §4.5 の「末尾委譲禁止」が規律でなく**機構的に不可能**になる
- `inv_svc_num / inv_caller_obj / inv_caller_thread` が完全に消える (PORT §4.6 予告の完成)
- kobj のルート委譲は「表引き → CALL_STRICT(svc番号, r1-r3)」に一本化。
  サブカーネルの「方針の局所性」は保たれ、さらに下への委譲も従来どおり kobj 経由

再訪条件: サブシステムが「kobj を 1 呼び出しごとに経由しない生 syscall 引き受け」を
性能上必要とした場合 — ただしそれは PORT §3.4 が会計成立のために明示的に退けた方向
なので、実測で問題が出てから議論すること。
